🎓 Theory Q&A — 5 Interview Questions
Q1. What is the SQL execution order? Why does it matter for a data analyst?
Hired answer: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. It matters because: (1) you cannot use a SELECT alias in a HAVING clause — the alias doesn't exist yet at HAVING execution time; (2) you cannot filter on an aggregate in WHERE — GROUP BY hasn't happened; (3) ORDER BY can use SELECT aliases because it runs last. In interviews, when asked "why doesn't this query work?" — 80% of the time the answer traces back to execution order.
Q2. What is the difference between COUNT(*) and COUNT(column)?
Hired answer: COUNT(*) counts every row including NULLs — it counts the row itself, not the value. COUNT(column) skips NULL values in that column — only counts rows where the column is NOT NULL. Common trap: if Eve has NULL revenue (no sales), COUNT(revenue) excludes her but COUNT(*) includes her. In BFSI analytics this matters enormously — counting customers vs counting transactions are different things.
Q3. What is the difference between WHERE and HAVING?
Hired answer: WHERE filters individual rows BEFORE grouping — it cannot reference aggregate functions. HAVING filters groups AFTER GROUP BY — it CAN reference aggregates like SUM(), COUNT(). Rule: if the filter is on a raw column value, use WHERE. If the filter is on a calculated aggregate, use HAVING. Mixing them up is one of the most common SQL interview failures.
Q4. In MySQL, what is the correct way to write string values in a query?
Hired answer: Single quotes — 'Alice', 'North', 'Loan'. Double quotes are for identifiers (column/table names with special characters) in MySQL's ANSI mode, but in standard MySQL mode double quotes around string values will throw an error or behave unexpectedly. Rule: always use single quotes for string literals in SQL. Using double quotes for strings is one of the most common Day 1 mistakes interviewers catch immediately.
Q5. What does DISTINCT do? When should you use it and when should you avoid it?
Hired answer: DISTINCT eliminates duplicate rows from the result set. Use it when you genuinely need unique values — e.g., SELECT DISTINCT region FROM sales to get a list of regions. Avoid it as a shortcut to "fix" unexpected duplicates — if your query returns duplicates unexpectedly, the real fix is correcting the JOIN condition, not slapping DISTINCT on top. In interviews: saying "I'd investigate why duplicates exist before using DISTINCT" signals senior thinking.
Task 1 — Filtering (45 min)

🎯 Business Ask: The Sales Head wants targeted lists of sales records based on multiple conditions. Write filtering queries using WHERE, AND/OR, BETWEEN, LIKE, and IN.

Query 1A — Basic WHERE + AND + OR

-- High-value Loan or Insurance deals in North or South regions
SELECT
    sale_id,
    rep_name,
    region,
    product,
    revenue,
    sale_date
FROM sales
WHERE revenue > 80000
  AND product IN ('Loan', 'Insurance')
  AND region IN ('North', 'South')
ORDER BY revenue DESC;

-- Expected: 3 rows — Alice Loan 120K, Alice Insurance 110K, Bob Insurance 85K
-- Business: Regional Head sees which high-value deals came from priority regions

Query 1B — BETWEEN + LIKE

-- Sales between Jan-Mar 2026 where rep name starts with 'A' or 'B'
SELECT
    rep_name,
    product,
    revenue,
    sale_date
FROM sales
WHERE sale_date BETWEEN '2026-01-01' AND '2026-03-31'
  AND (rep_name LIKE 'A%' OR rep_name LIKE 'B%')
ORDER BY sale_date;

-- BETWEEN is inclusive on both ends
-- LIKE 'A%' = starts with A · '%A%' = contains A · '_lice' = any char + lice
-- Expected: Alice Jan, Bob Feb — 2 rows

Query 1C — NOT IN + IS NOT NULL

-- All sales except Deposit product, where revenue is not null
SELECT
    rep_name,
    region,
    product,
    revenue
FROM sales
WHERE product NOT IN ('Deposit')
  AND revenue IS NOT NULL
ORDER BY revenue DESC;

-- Expected: 5 rows (all except Dave's Deposit deal)
-- IS NOT NULL — never write != NULL or <> NULL → those never match!
Task 2 — Aggregation + GROUP BY + HAVING (45 min)

🎯 Business Ask: Produce a revenue summary by region and product. Filter to show only groups with meaningful revenue. Sort by highest revenue first.

Query 2A — GROUP BY + All Aggregates

SELECT
    region,
    COUNT(*)                    AS num_deals,
    SUM(revenue)                AS total_revenue,
    ROUND(AVG(revenue), 0)     AS avg_revenue,
    MAX(revenue)                AS highest_deal,
    MIN(revenue)                AS lowest_deal
FROM sales
GROUP BY region
ORDER BY total_revenue DESC;

-- North: 2 deals, 230K total · South: 2 deals, 160K · East: 95K · West: 60K
-- Business: North is the star region — allocate more resources there

Query 2B — HAVING to Filter Groups

SELECT
    product,
    COUNT(*)             AS num_deals,
    SUM(revenue)         AS total_revenue,
    ROUND(AVG(revenue),0) AS avg_deal_size
FROM sales
GROUP BY product
HAVING SUM(revenue) > 150000   -- ✅ aggregate in HAVING, NOT in WHERE
ORDER BY total_revenue DESC;

-- Only Loan (290K) and Insurance (195K) pass the 150K threshold
-- Deposit (60K) is filtered OUT by HAVING
-- Business: focus product training on Loan and Insurance — highest revenue

Query 2C — WHERE + GROUP BY + HAVING Combined

-- Pre-filter rows (WHERE), then group, then filter groups (HAVING)
SELECT
    rep_name,
    COUNT(*)              AS deals,
    SUM(revenue)          AS total_revenue
FROM sales
WHERE sale_date >= '2026-01-01'     -- row-level filter first
  AND product != 'Deposit'           -- exclude Deposit before grouping
GROUP BY rep_name
HAVING COUNT(*) >= 2               -- only reps with 2+ qualifying deals
ORDER BY total_revenue DESC;

-- Only Alice qualifies (2 Loan+Insurance deals, no Deposit)
-- Business: Alice is the multi-product champion — identify for mentoring role
Task 3 — Data Audit with CASE WHEN (40 min)

🎯 Business Ask: The Data Quality team needs a flag on every sales record — High/Mid/Low revenue band, deal quarter, and whether the revenue seems anomalous.

Query 3A — CASE WHEN for Revenue Banding

SELECT
    sale_id,
    rep_name,
    region,
    product,
    revenue,
    sale_date,
    -- Revenue band
    CASE
        WHEN revenue >= 100000             THEN 'High (>=100K)'
        WHEN revenue >= 75000              THEN 'Mid (75K–99K)'
        ELSE                                    'Low (<75K)'
    END                                     AS revenue_band,
    -- Quarter label
    CASE
        WHEN MONTH(sale_date) BETWEEN 1 AND 3  THEN 'Q1'
        WHEN MONTH(sale_date) BETWEEN 4 AND 6  THEN 'Q2'
        WHEN MONTH(sale_date) BETWEEN 7 AND 9  THEN 'Q3'
        ELSE                                        'Q4'
    END                                     AS quarter
FROM sales
ORDER BY revenue DESC;

-- 6 rows flagged: Alice 120K=High, Alice 110K=High, Carol 95K=Mid,
--                 Bob 85K=Mid, Bob 75K=Mid, Dave 60K=Low
-- Business: Data quality team sees distribution instantly

Query 3B — CASE WHEN Inside GROUP BY (Conditional Aggregation)

SELECT
    region,
    COUNT(*)                                              AS total_deals,
    SUM(CASE WHEN revenue >= 100000 THEN 1 ELSE 0 END)  AS high_value_deals,
    SUM(CASE WHEN revenue >= 100000
                 THEN revenue ELSE 0 END)               AS high_value_revenue,
    SUM(CASE WHEN product = 'Loan'
                 THEN revenue ELSE 0 END)               AS loan_revenue
FROM sales
GROUP BY region
ORDER BY high_value_revenue DESC;

-- This is the "pivot without PIVOT" technique — crucial for BFSI reporting
-- North: 2 high-value deals, 230K high-value rev, 120K loan rev
-- Business: North dominates both metrics — budget priority confirmed
Task 4 — Business KPI with Subquery (25 min)

🎯 Business Ask: Show each product's revenue AND its % contribution to total revenue. This is the most common BFSI dashboard KPI.

Query 4A — % Contribution via Subquery

SELECT
    product,
    COUNT(*)                                          AS num_deals,
    SUM(revenue)                                      AS product_revenue,
    ROUND(
        SUM(revenue) * 100.0 /
        (SELECT SUM(revenue) FROM sales),            -- subquery for grand total
    1)                                                AS pct_of_total
FROM sales
GROUP BY product
ORDER BY product_revenue DESC;

-- Grand total: SELECT SUM(revenue) FROM sales = 545,000
-- Loan: 290K = 53.2% · Insurance: 195K = 35.8% · Deposit: 60K = 11.0%
-- Business: Loan dominates 53% — credit risk concentration flag for Risk team

Query 4B — Top-N Query (Top 2 Reps by Revenue)

SELECT
    rep_name,
    COUNT(*)      AS deals,
    SUM(revenue)  AS total_revenue
FROM sales
GROUP BY rep_name
ORDER BY total_revenue DESC
LIMIT 2;

-- Alice: 230,000 (2 deals) · Bob: 160,000 (2 deals)
-- Alice + Bob = 390K / 545K = 71.6% of total revenue
-- Business: Key-person risk — 2 reps drive 72% of revenue

📄 Day 1 Cheat Sheet — SQL Foundations

⚙ Execution Order + Clause Rules

-- Correct order to WRITE a query
SELECT   col, SUM(rev) AS total  -- ⑤
FROM     sales                   -- ①
WHERE    product = 'Loan'        -- ② rows
GROUP BY col                     -- ③
HAVING   SUM(rev) > 100000     -- ④ groups
ORDER BY total DESC             -- ⑥
LIMIT    10;                     -- ⑦

-- Key rules:
-- WHERE  → raw column values only
-- HAVING → aggregates only
-- HAVING uses SUM(rev), NOT alias 'total'
-- Alias created at SELECT (step 5)
--   usable only in ORDER BY (step 6)

🔍 WHERE Operators

-- Comparison
WHERE rev > 100000
WHERE rev >= 100000
WHERE rev != 60000

-- Range
WHERE rev BETWEEN 75000 AND 120000
-- inclusive both ends

-- List
WHERE product IN ('Loan','Insurance')
WHERE region NOT IN ('West')

-- Pattern
WHERE rep_name LIKE 'A%'   -- starts with A
WHERE rep_name LIKE '%ob'  -- ends with ob
WHERE rep_name LIKE '%li%' -- contains li

-- NULL
WHERE col IS NULL      -- ✅
WHERE col IS NOT NULL  -- ✅
WHERE col = NULL       -- ❌ never matches

📊 Aggregates + GROUP BY

-- All 5 aggregate functions
COUNT(*)        -- all rows incl. NULLs
COUNT(col)      -- non-NULL rows only
SUM(revenue)    -- ignores NULLs
AVG(revenue)    -- ignores NULLs
MAX(revenue)
MIN(revenue)

-- ROUND for clean output
ROUND(AVG(revenue), 0)  -- 0 decimals
ROUND(x * 100.0 / y, 1) -- % with 1dp

-- HAVING (never WHERE for aggregates)
HAVING SUM(revenue) > 150000
HAVING COUNT(*) >= 2

-- % contribution subquery
SUM(rev) * 100.0 /
  (SELECT SUM(rev) FROM sales)

🔀 CASE WHEN Patterns

-- Simple label
CASE
  WHEN rev >= 100000 THEN 'High'
  WHEN rev >= 75000  THEN 'Mid'
  ELSE 'Low'
END AS rev_band

-- Conditional count (pivot style)
SUM(CASE WHEN product='Loan'
         THEN 1 ELSE 0 END)
  AS loan_count

-- Conditional revenue
SUM(CASE WHEN rev>100000
         THEN rev ELSE 0 END)
  AS high_rev

-- Quarter from date
CASE QUARTER(sale_date)
  WHEN 1 THEN 'Q1'
  WHEN 2 THEN 'Q2'
  ELSE 'Q3/Q4'
END

⚖ What Gets You HIRED vs REJECTED on Day 1

❌ Rejected

  • Says SELECT comes first in SQL execution order
  • Uses double quotes for string values — syntax error in MySQL
  • Writes HAVING total_rev > 100000 using alias — query fails
  • Writes WHERE SUM(revenue) > 100000 — aggregate in WHERE
  • Says COUNT(*) and COUNT(column) are identical
  • Writes WHERE revenue = NULL — returns 0 rows always
  • Submits query without re-reading the requirement
  • Gives numbers without any business interpretation

✅ Hired

  • States execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
  • Always single quotes for string literals — never double
  • HAVING uses full aggregate: HAVING SUM(revenue) > 100000
  • Explains COUNT(*) counts NULLs; COUNT(col) skips NULLs
  • Uses IS NULL / IS NOT NULL — never = NULL
  • Re-reads every requirement before submitting
  • Adds business context: "North drives 42% of revenue — prioritise budget here"
  • Uses ROUND() for clean output — signals production-quality thinking
