Concept Filter Context — Most Important DAX Concept

What is Filter Context?

The set of filters active when a DAX expression is evaluated. The SAME measure returns DIFFERENT values depending on what filters are active.

SituationSUM(sales[revenue]) returns
No slicer selected₹63,201.50 (all rows)
User clicks "North" on region slicer₹21,800.00 (North only)
User clicks "Enterprise" on team slicer₹27,300.00 (Enterprise reps only)
CALCULATE = the function that lets you MODIFY or OVERRIDE filter context. It is the most important DAX function. No CALCULATE = can't build % of total, YoY, team-specific KPIs.

Interview Q&A 10 Questions — MNC Level

Q1 What is a star schema and why do you use it in Power BI?
"A star schema has one central fact table with metrics and foreign keys, surrounded by dimension tables with descriptive attributes. I use it because it gives clean, predictable filter flow — slicers on dimensions automatically filter the fact table. It also improves query performance and makes DAX simpler. A flat denormalized table creates data redundancy, inflated file size, and complex DAX."
Tests: data modeling fundamentals Trap: "I load everything into one table" — instant red flag Keywords: fact · dimension · filter flow · performance · normalized
Q2 Difference between Measure and Calculated Column?
"A measure is computed at query time and responds to filter context — slicers affect it. A calculated column is computed once at load and stored statically — slicers don't affect it. For KPIs: always measures. For row labels like tier or category: calculated column. The key reason is performance — measures scale to millions of rows efficiently, calculated columns bloat file size."
Tests: most asked Power BI question in every MNC Trap: using calculated columns for revenue totals — performance disaster on BFSI data
Q3 What does CALCULATE do in DAX?
"CALCULATE evaluates a DAX expression inside a modified filter context. It takes an expression and filter arguments that override or add to the existing context. For example, CALCULATE(SUM(sales[revenue]), sales[region] = 'North') always returns North's revenue regardless of slicer selection. Without CALCULATE you can't override filter context — so you can't build % of total, same-period-last-year, or team-specific KPIs."
Tests: CALCULATE is the most important DAX function — tested 100% of interviews Trap: Confusing CALCULATE with FILTER — FILTER returns a table, CALCULATE evaluates an expression
Q4 What is ALL() and when do you use it?
"ALL() removes all filters from a table or column, returning unfiltered results regardless of slicers. Most common use: % of total — DIVIDE(SUM(revenue), CALCULATE(SUM(revenue), ALL(sales))). Without ALL(), the denominator is also filtered and every row shows 100%. ALLSELECTED() is the variant that keeps slicer selections — used when you want % within the user's filtered view."
Tests: ALL vs ALLSELECTED is a Persistent favourite follow-up Trap: Using ALL() when ALLSELECTED() is the business requirement
Q5 How do you set up relationships in Power BI?
"In Model view, drag primary key from dimension to foreign key in fact table. I verify three things: cardinality is One-to-Many (dimension to fact), cross-filter direction is Single (filters flow one way), and relationship is Active. I never use bidirectional filtering unless there's a specific reason — it creates ambiguous filter paths in complex models."
Tests: real modeling experience not just UI clicking Trap: bidirectional filtering on everything — signals amateur modeling
Q6 What is Power Query used for?
"Power Query is the transformation layer — runs before data loads into the model. I use it to fix data types, remove duplicates, rename columns to business-friendly names, filter nulls, unpivot columns, and merge sources. Anything fixable in Power Query I fix there — not in DAX. Clean data in means simpler measures and fewer errors. This matters especially for BFSI data which is always dirty."
Trap: "I fix data issues in DAX" — Power Query transforms are more efficient and transparent
Q7 Write the DAX for Revenue % of Total.
Revenue % of Total =
VAR current_rev = SUM(sales[revenue])
VAR total_rev   = CALCULATE(SUM(sales[revenue]), ALL(sales))
RETURN DIVIDE(current_rev, total_rev, 0) * 100
"I use VAR to store each part — avoids computing SUM twice, faster on large models. DIVIDE handles division by zero gracefully with 0 as fallback. ALL(sales) removes all filters so denominator is always grand total."
Tests: exact measure asked in almost every Power BI interview Trap: Not using VAR (computes SUM twice) · Not using DIVIDE (crashes on empty data)
Q8 ALL() vs ALLSELECTED() — difference?
ALL()ALLSELECTED()
Removes slicer filters✅ Yes❌ No — keeps them
Use case% of grand total (always fixed)% within user's selection
% adds up toMay not total 100% in selectionAlways 100% within selection
"If user filters to North and I want North's % of ALL regions — use ALL(). If I want North's % only within user's selected regions — use ALLSELECTED(). Business context decides which is correct."
Q9 A slicer is not filtering a visual — how do you debug?
"Three places to check: First, is the relationship active between the slicer table and the visual's table? Go to Model view and verify. Second, is the cross-filter direction correct — does it flow from the slicer table toward the visual table? Third, is there a visual-level filter overriding the slicer? Check the visual's filter pane. If the relationship is inactive I'll use USERELATIONSHIP() in a CALCULATE measure to activate it for that specific calculation."
Tests: real troubleshooting experience Keywords: relationship · filter direction · USERELATIONSHIP · visual filter
Q10 Star schema vs Snowflake schema — difference?
Star SchemaSnowflake Schema
Dimension tablesDenormalized (flat)Normalized (split further)
JoinsFewer — faster queriesMore — slower queries

"In Power BI I always prefer star schema — fewer hops, simpler DAX, faster visuals. Snowflake adds unnecessary joins and slows filter propagation. For BFSI dashboards that need sub-second response, star schema is the standard."

Case Study Revenue Discrepancy Scenario

📋 Scenario

"North region manager claims 108% target achievement. Your Power BI dashboard shows 87%. Manager is furious. Find the discrepancy."

  1. Check the measure definition
    Is Achievement % using the correct tables? Is target coming from reps or a different source?
  2. Check the relationship between reps and sales
    Is the One-to-Many relationship active? Is filter direction correct?
  3. Check the date range
    Is the dashboard filtered to August only? Manager may be including September. Check slicer settings.
  4. Cross-validate against SQL
    Run the same aggregation in MySQL — if SQL shows 108% and Power BI shows 87%, the model has a data issue
  5. Check if Eve (no sales) is included in Target Total
    Eve's ₹16,000 target is included in denominator — inflating the total target, deflating the % achievement
  6. Present findings with evidence
    Show the query output, measure code, and relationship screenshot — not just a number

🎯 5 Things a Persistent Power BI Interviewer Expects

  1. Star schema model — not flat table. Every BFSI dashboard at Persistent uses star schema. If you say "I put everything in one table" the interview ends.
  2. Measures for KPIs, Calculated Columns for row labels. No exceptions. Calculated columns for revenue = instant junior signal.
  3. CALCULATE + ALL for % of total — from memory. This exact measure is asked in every Power BI interview. Write it with VAR + DIVIDE — no shortcuts.
  4. Single-direction relationships only unless specifically justified. Bidirectional = ambiguous filter path = wrong numbers for client.
  5. Power Query for cleaning, not DAX. Fix data types, nulls, duplicates in Power Query. Clean data in = simpler DAX = fewer dashboard errors.
