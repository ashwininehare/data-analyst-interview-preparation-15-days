🔗 The 4 JOIN Types — Know All 4 Cold
INNER JOIN
Only rows that match in BOTH tables. Eve disappears — no sales.
Matching rows only
LEFT JOIN
All rows from LEFT table + matching rows from right. Eve stays with NULLs.
All LEFT + match RIGHT
RIGHT JOIN
All rows from RIGHT table + matching rows from left. Rarely used — rewrite as LEFT JOIN.
All RIGHT + match LEFT
FULL OUTER
All rows from both tables. NULLs on non-matching side. MySQL: emulate with UNION.
All rows both sides

🎓 Theory Q&A — 5 Interview Questions
Q1. What is the difference between INNER JOIN and LEFT JOIN? When does a row "disappear"?
Hired answer: INNER JOIN returns only rows where the join condition is satisfied in BOTH tables. If a row in the left table has no matching row in the right table, it is excluded from the result — it "disappears." LEFT JOIN returns ALL rows from the left table regardless of whether a match exists in the right table; non-matching rows from the right side appear as NULL. In BFSI analytics: if I JOIN reps to sales using INNER JOIN, Eve (who has no sales) disappears — my revenue report now silently under-counts the team. This is a data quality failure. Default instinct: start with LEFT JOIN when the left table is your primary entity (reps, customers, accounts).
Q2. What is a CTE (WITH clause)? How is it different from a subquery?
Hired answer: A CTE (Common Table Expression) is a named temporary result set defined at the top of a query using the WITH keyword. Both CTEs and subqueries achieve the same result — break a complex query into steps — but CTEs are: (1) Readable — defined once at the top, referenced by name below; (2) Reusable — a CTE can be referenced multiple times in the same query; (3) Recursive — CTEs support recursion, subqueries do not. Persistent prefers CTEs because they make query logic transparent — interviewers can follow your reasoning step by step.
Q3. What are the three types of subqueries? Give a one-line example of each.
Hired answer:
(1) WHERE subquery — filters rows: WHERE revenue > (SELECT AVG(revenue) FROM sales)
(2) FROM subquery (derived table) — used as a virtual table: FROM (SELECT region, SUM(revenue) AS tot FROM sales GROUP BY region) AS r
(3) SELECT subquery (scalar) — returns a single value inside SELECT: SELECT rep_name, revenue, (SELECT SUM(revenue) FROM sales) AS grand_total
In BFSI: WHERE subquery = "show deals above average deal size"; FROM subquery = "rank regions by their aggregated totals"; SELECT subquery = "% contribution per row."
Q4. You have a query with INNER JOIN reps and sales. You expect 5 rows (one per rep) but get 4. What happened and how do you fix it?
Hired answer: Eve has no records in the sales table. INNER JOIN requires a matching row in BOTH tables — since Eve has no sales, her rep record is excluded from the result. The fix is to change INNER JOIN to LEFT JOIN with reps as the left table: FROM reps r LEFT JOIN sales s ON r.rep_name = s.rep_name. Then wrap the revenue aggregate with COALESCE: COALESCE(SUM(s.revenue), 0) so Eve shows ₹0 instead of NULL. This is the "Eve test" — if your query can't account for reps with no activity, it fails a basic data completeness check.
Q5. When should you use a CTE vs a subquery vs a temporary table?
Hired answer:
CTE — use when the intermediate result is complex, needs a readable name, or is referenced more than once in the same query. Best for interview queries and production code where clarity matters.
Subquery — use for simple, one-off inline filters or scalar values. Acceptable for short logic but gets unreadable when nested 3+ levels deep.
Temporary table — use when the intermediate result is large (millions of rows), needs an index, or is used across multiple separate queries in a session. Overkill for most analytical queries.
Rule of thumb: CTE for readability, subquery for simplicity, temp table for performance at scale.
Task 1 — JOINs (45 min)

🎯 Business Ask: The HR team needs a complete rep performance report including reps with zero sales. The Ops team needs sales enriched with region zone and manager data.

Query 1A — LEFT JOIN: All Reps Including Eve

SELECT
    r.rep_name,
    r.team,
    r.target,
    COALESCE(SUM(s.revenue), 0)          AS actual_revenue,
    COALESCE(COUNT(s.sale_id), 0)          AS num_deals,
    ROUND(
        COALESCE(SUM(s.revenue), 0)
        * 100.0 / r.target,
    1)                                     AS pct_of_target
FROM reps r
LEFT JOIN sales s ON r.rep_name = s.rep_name
GROUP BY r.rep_name, r.team, r.target
ORDER BY actual_revenue DESC;

-- 5 rows: Alice 230K(115%), Carol 95K(63%), Bob 160K(89%), Dave 60K(50%), Eve 0(0%)
-- COALESCE(SUM(s.revenue), 0) → Eve shows 0 not NULL
-- Business: HR sees complete team health — Eve needs urgent intervention

Query 1B — 3-Table JOIN: sales + reps + regions

SELECT
    s.sale_id,
    s.rep_name,
    r.team,
    s.region,
    rg.zone,
    rg.manager,
    s.product,
    s.revenue,
    s.sale_date
FROM sales s
INNER JOIN reps r     ON s.rep_name = r.rep_name
INNER JOIN regions rg ON s.region   = rg.region
ORDER BY s.revenue DESC;

-- 6 rows with team, zone, manager columns enriched
-- INNER JOIN is correct here — every sale has a rep AND a region
-- Business: Ops team can now filter by zone (Zone-A vs Zone-B) for territory reporting

Query 1C — LEFT JOIN to Find "Gap" Rows (Anti-JOIN Pattern)

-- Find reps who have NEVER made a sale (the "missing" pattern)
SELECT
    r.rep_name,
    r.team,
    r.hire_date,
    r.target
FROM reps r
LEFT JOIN sales s ON r.rep_name = s.rep_name
WHERE s.sale_id IS NULL    -- keeps only reps with NO match in sales
ORDER BY r.hire_date;

-- Result: Eve (1 row) — she has no sales, so sale_id IS NULL after LEFT JOIN
-- This is the Anti-JOIN pattern: LEFT JOIN + WHERE right_key IS NULL
-- Business: "Which reps onboarded after July 2024 have zero sales?" → escalate to manager
Task 2 — Subqueries (40 min)

🎯 Business Ask: Show deals above the average deal size. Rank regions by their total revenue. Show each sale's % of grand total inline.

Query 2A — WHERE Subquery: Above-Average Deals

SELECT
    rep_name,
    region,
    product,
    revenue,
    ROUND((SELECT AVG(revenue) FROM sales), 0) AS avg_deal_size
FROM sales
WHERE revenue > (SELECT AVG(revenue) FROM sales)
ORDER BY revenue DESC;

-- AVG(revenue) = 545000/6 = 90,833
-- Above average: Alice Loan 120K, Alice Insurance 110K, Carol Loan 95K
-- 3 rows returned
-- Business: Focus account management effort on these 3 deals for upsell/renewal

Query 2B — FROM Subquery (Derived Table): Region Revenue Rank

SELECT
    region_summary.region,
    region_summary.total_revenue,
    region_summary.num_deals,
    RANK() OVER (ORDER BY region_summary.total_revenue DESC) AS revenue_rank
FROM (
    SELECT
        region,
        SUM(revenue)  AS total_revenue,
        COUNT(*)      AS num_deals
    FROM sales
    GROUP BY region
) AS region_summary
ORDER BY revenue_rank;

-- Derived table = subquery in FROM clause — must be aliased (AS region_summary)
-- North rank 1 (230K), South rank 2 (160K), East rank 3 (95K), West rank 4 (60K)
-- Business: Budget allocation priority order for next quarter

Query 2C — SELECT Subquery (Scalar): Inline % of Grand Total

SELECT
    rep_name,
    region,
    product,
    revenue,
    (SELECT SUM(revenue) FROM sales)             AS grand_total,
    ROUND(
        revenue * 100.0 /
        (SELECT SUM(revenue) FROM sales),
    1)                                             AS pct_of_grand_total
FROM sales
ORDER BY pct_of_grand_total DESC;

-- Grand total = 545,000 on every row (scalar subquery = single value)
-- Alice Loan = 120000/545000 = 22.0%
-- Business: "Alice's Jan Loan deal alone = 22% of entire H1 revenue"
Task 3 — CTEs (45 min)

🎯 Business Ask: Rewrite the subquery approach using CTEs for clarity. Then chain two CTEs to produce a rep performance scorecard with status labels.

Query 3A — Single CTE: Rep Revenue Summary

WITH rep_revenue AS (
    SELECT
        rep_name,
        SUM(revenue)   AS total_revenue,
        COUNT(sale_id)  AS num_deals,
        MAX(sale_date)  AS last_sale_date
    FROM sales
    GROUP BY rep_name
)
SELECT
    r.rep_name,
    r.team,
    r.target,
    COALESCE(rr.total_revenue, 0)   AS actual_revenue,
    COALESCE(rr.num_deals, 0)        AS deals,
    COALESCE(rr.last_sale_date, 'Never') AS last_sale
FROM reps r
LEFT JOIN rep_revenue rr ON r.rep_name = rr.rep_name
ORDER BY actual_revenue DESC;

-- CTE replaces the subquery in FROM — cleaner, readable, same result
-- Eve appears with revenue=0, deals=0, last_sale='Never'

Query 3B — Chained CTEs: Performance Scorecard with Status

WITH rep_actuals AS (
    -- CTE 1: Aggregate sales per rep
    SELECT
        rep_name,
        SUM(revenue)   AS actual_revenue,
        COUNT(*)        AS num_deals
    FROM sales
    GROUP BY rep_name
),
rep_scorecard AS (
    -- CTE 2: Join to reps, calculate % of target, assign status
    SELECT
        r.rep_name,
        r.team,
        r.target,
        COALESCE(ra.actual_revenue, 0)   AS actual_revenue,
        COALESCE(ra.num_deals, 0)         AS deals,
        ROUND(
            COALESCE(ra.actual_revenue, 0)
            * 100.0 / r.target,
        1)                                 AS pct_of_target
    FROM reps r
    LEFT JOIN rep_actuals ra ON r.rep_name = ra.rep_name
)
-- Final SELECT: add status label from CTE 2 results
SELECT
    rep_name,
    team,
    target,
    actual_revenue,
    deals,
    pct_of_target,
    CASE
        WHEN pct_of_target >= 100 THEN '🟢 On Track'
        WHEN pct_of_target >= 80  THEN '🟡 At Risk'
        ELSE                           '🔴 Underperforming'
    END                              AS status
FROM rep_scorecard
ORDER BY pct_of_target DESC;

-- Alice 115% 🟢 · Bob 89% 🟡 · Carol 63% 🔴 · Dave 50% 🔴 · Eve 0% 🔴
-- CASE WHEN uses pct_of_target alias — valid here (SELECT reads from CTE, no execution order issue)
-- Business: HR scorecard — 3 of 5 reps underperforming → team-level intervention needed
Task 4 — CTE + JOIN + Subquery Combined (25 min)

🎯 Business Ask: For each region, show: total revenue, its % of grand total, the top rep in that region, and the zone manager. This is a real BFSI dashboard query.

Query 4 — Full Business Dashboard Query

WITH region_totals AS (
    -- CTE 1: Revenue per region
    SELECT
        region,
        SUM(revenue)   AS region_revenue,
        COUNT(*)        AS num_deals
    FROM sales
    GROUP BY region
),
top_reps AS (
    -- CTE 2: Top rep per region (by revenue)
    SELECT
        region,
        rep_name,
        SUM(revenue) AS rep_revenue,
        RANK() OVER (
            PARTITION BY region
            ORDER BY SUM(revenue) DESC
        )             AS rep_rank
    FROM sales
    GROUP BY region, rep_name
)
SELECT
    rt.region,
    rg.zone,
    rg.manager,
    rt.region_revenue,
    rt.num_deals,
    ROUND(
        rt.region_revenue * 100.0 /
        (SELECT SUM(revenue) FROM sales),   -- scalar subquery for grand total
    1)                                       AS pct_of_total,
    tr.rep_name                              AS top_rep
FROM region_totals rt
INNER JOIN regions rg  ON rt.region = rg.region
INNER JOIN top_reps tr ON rt.region = tr.region
    AND tr.rep_rank = 1                     -- only the #1 rep per region
ORDER BY rt.region_revenue DESC;

-- North: Zone-A, Rajesh, 230K, 42.2%, Alice
-- South: Zone-B, Priya,  160K, 29.4%, Bob
-- East:  Zone-A, Amit,    95K, 17.4%, Carol
-- West:  Zone-B, Sunita,  60K, 11.0%, Dave
-- Business: Complete regional dashboard — revenue, share, owner, escalation contact

📄 Day 2 Cheat Sheet — JOINs · Subqueries · CTEs

🔗 JOIN Patterns

-- INNER: only matching rows
FROM sales s
INNER JOIN reps r
    ON s.rep_name = r.rep_name

-- LEFT: keep ALL left rows
FROM reps r
LEFT JOIN sales s
    ON r.rep_name = s.rep_name
-- Eve stays! Revenue = NULL
-- Fix: COALESCE(SUM(s.revenue),0)

-- 3-table JOIN
FROM sales s
INNER JOIN reps r
    ON s.rep_name = r.rep_name
INNER JOIN regions rg
    ON s.region = rg.region

-- Anti-JOIN (find non-matches)
FROM reps r
LEFT JOIN sales s ON ...
WHERE s.sale_id IS NULL

🔍 3 Subquery Types

-- WHERE subquery (filter rows)
WHERE revenue >
  (SELECT AVG(revenue)
   FROM sales)

-- FROM subquery (derived table)
-- MUST have alias!
FROM (
  SELECT region,
    SUM(revenue) AS tot
  FROM sales
  GROUP BY region
) AS reg_summary

-- SELECT scalar subquery
SELECT rep_name, revenue,
  (SELECT SUM(revenue)
   FROM sales) AS grand_total,
  revenue * 100.0 /
  (SELECT SUM(revenue)
   FROM sales) AS pct

🧱 CTE Syntax

-- Single CTE
WITH cte_name AS (
    SELECT col1, SUM(rev) AS tot
    FROM sales
    GROUP BY col1
)
SELECT * FROM cte_name;

-- Chained CTEs (comma-separated)
WITH
cte_one AS (
    SELECT ... FROM sales
),
cte_two AS (
    SELECT ...
    FROM reps r
    LEFT JOIN cte_one c
        ON r.rep_name = c.rep_name
)
SELECT *,
  CASE WHEN pct >= 100
       THEN 'On Track'
       ELSE 'At Risk' END AS status
FROM cte_two;

⚠ Day 2 Traps + Fixes

-- TRAP 1: INNER JOIN loses Eve
Fix: LEFT JOIN from reps → sales

-- TRAP 2: NULL revenue after LEFT JOIN
COALESCE(SUM(s.revenue), 0)
-- or COALESCE(s.revenue, 0)

-- TRAP 3: FROM subquery no alias
Fix: always add AS alias_name
FROM (SELECT ...) AS my_alias

-- TRAP 4: CTE not terminated
Fix: comma after each CTE block
WITH cte1 AS (...),   -- comma
     cte2 AS (...)    -- no comma on last
SELECT ...;

-- TRAP 5: = NULL instead of IS NULL
WHERE s.sale_id IS NULL  -- ✅
WHERE s.sale_id = NULL   -- ❌
⚖ What Gets You HIRED vs REJECTED on Day 2

❌ Rejected

  • Uses INNER JOIN on reps → sales — Eve disappears, result has 4 rows not 5
  • Doesn't add COALESCE — Eve shows NULL revenue in report
  • Writes FROM subquery without alias — MySQL syntax error
  • Can't explain difference between CTE and subquery
  • Nests 3 levels of subqueries — unreadable, unmaintainable
  • Uses WHERE sale_id = NULL for anti-join — returns 0 rows
  • Says "I'd just use INNER JOIN — it's simpler" without thinking about completeness
  • Output has numbers but zero business interpretation

✅ Hired

  • States LEFT JOIN rationale before writing: "reps is the primary entity — all reps must appear"
  • COALESCE(SUM(s.revenue), 0) on every LEFT JOIN revenue column — automatic reflex
  • FROM subquery always aliased — never forgets
  • Chooses CTE over nested subqueries — cites readability + reusability
  • Anti-JOIN pattern: LEFT JOIN + WHERE right_key IS NULL — not NOT IN
  • Chains 2 CTEs cleanly — comma placement correct, final SELECT references both
  • Validates result: "5 rows — Eve present with 0 revenue — data complete"
  • Business insight: "3 of 5 reps underperforming — team intervention needed by Q3"
